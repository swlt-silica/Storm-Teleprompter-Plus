# ASR 发音容错与旗舰流式模型设计

## 意图

改善 Android 普通提词和悬浮窗的本机语音跟随。说话人存在同音字、前鼻音与后鼻音、平舌音与翘舌音差异时，提词位置仍应沿着正在朗读的原稿前进。高性能 Android 手机可以使用更大的流式模型，提升中文和中英混合稿件的识别质量。

## 当前问题

- `TeleprompterAlignment` 只按字符完全相等匹配，识别结果出现同音字或声母、韵母差异时会降低匹配长度。
- 当前模型列表主要是 2023 年的 Zipformer 模型，推荐逻辑按处理器核心数判断，没有提供面向高内存手机的旗舰档位。
- 当前本机识别使用 `sherpa_onnx` 的 `OnlineRecognizer`，模型目录按 `tokens.txt`、`encoder`、`decoder`、可选 `joiner` 加载，适合继续接入流式 Transducer 模型。
- 提词器需要持续滚动，模型必须提供连续的中间结果。需要保持在线识别接口，避免改成等待整句结束的离线识别流程。

## 目标

- 对中文对齐增加可控的发音宽松匹配。
- 默认允许常见同音和普通话音系差异参与匹配，同时保留足够长的连续匹配门槛，避免单个相似字造成跳段。
- 新增高准确率的中英流式旗舰模型，提供低延迟和高准确率两个档位。
- 让模型列表显示模型大小、延迟和推荐内存，支持用户在手机上直接下载和切换。
- 普通提词与悬浮窗共用同一套模型和对齐逻辑。
- 完成 Flutter 测试、Android ARM64 Release 构建和 GitHub Release 发布。

## 非目标

- 本次不改成完全离线分段识别。
- 本次不加入第二个离线模型做句后复核。
- 本次不修改稿件内容，也不把识别到的错别字写回原稿。
- 本次不把宽松匹配应用到英文单词内部的任意字符替换。

## 方案比较

### 方案一，流式大模型加发音宽松对齐

保留当前 `OnlineRecognizer` 和滚动流程，在对齐引擎内部增加中文发音等价层，并新增官方中英流式 Zipformer 旗舰模型。这个方案可以持续输出中间结果，改动集中，适合提词器的即时滚动需求。本次采用该方案。

### 方案二，流式识别加离线模型复核

流式模型负责即时滚动，保存最近音频，句末用离线 SenseVoice 或 Whisper 复核。准确率上限更高，但需要新增 `OfflineRecognizer`、音频缓存、句子重定位和更多内存控制，可能产生句末跳动。本次暂不采用。

### 方案三，完全使用大离线模型分段识别

使用大模型按短句识别后再推进提词位置。实现路径更接近录音转写，识别等待会直接影响跟嘴体验。本次暂不采用。

## 模型选择

第一批接入官方 `x-ASR` 中英流式 Zipformer 模型，使用标准精度包以利用高性能手机的内存，并同时保留 INT8 包作为低内存和低存储选项。

- 旗舰高准确率：`sherpa-onnx-x-asr-960ms-streaming-zipformer-transducer-zh-en-punct-2026-06-05`
- 旗舰低延迟：`sherpa-onnx-x-asr-480ms-streaming-zipformer-transducer-zh-en-punct-2026-06-05`
- 兼容量化：对应的 `*-int8-*` 包

默认推荐 960ms 标准精度模型。设置页允许切换 480ms、960ms 和现有模型。应用不根据 Android 的总运存自动下载大文件，用户明确选择模型后才下载。模型下载、解压和加载失败时保留现有模型，不能破坏已经可用的跟读功能。

模型加载器继续根据模型目录中的文件识别 `tokens.txt`、`encoder*.onnx`、`decoder*.onnx` 和 `joiner*.onnx`。如果新模型要求指定 `modelType`，模型元数据中保存该值，加载时传给 `OnlineModelConfig`。

## 发音宽松对齐

新增独立的中文发音匹配表示，不改变显示文本和原稿索引。对每个中文字符生成用于比较的等价类别，至少覆盖：

- 同音字和常见口语误识别字
- `n` 与 `ng` 的前后鼻音差异
- `z` 与 `zh`、`c` 与 `ch`、`s` 与 `sh` 的平翘舌差异
- `l` 与 `n`、`f` 与 `h` 等普通话口语中较常见的声母混淆
- `an` 与 `ang`、`en` 与 `eng`、`in` 与 `ing`、`ian` 与 `iang` 等韵母混淆

匹配采用分层策略。

1. 完全相同字符优先，保持当前结果稳定。
2. 中文字符在发音等价时计为低权重匹配。
3. 英文、数字和混合片段继续使用大小写折叠与原有字符匹配。
4. 宽松匹配必须满足连续片段长度和整体比例门槛，短片段不能触发远距离跳转。
5. 只有最终结果或达到较高连续匹配长度时，才提交稳定锚点。

对齐结果增加策略标识，便于日志和测试区分完全匹配与发音容错匹配。宽松匹配产生的原稿位置仍使用原始字符索引，滚动位置和手动跳转保持兼容。

## 模型设置和默认行为

- 模型卡片显示中文或中英支持范围、压缩包大小、推荐内存、延迟档位和准确率定位。
- 默认模型改为已下载模型中准确率最高且满足设备条件的模型。首次使用时优先推荐 960ms 标准精度旗舰模型。
- 用户已有模型继续保留，不自动删除、不自动替换。
- 普通提词和悬浮窗读取同一个 `AppSettings.asrModelId`。
- 模型切换发生在下一次开始识别前，运行中的会话不强制重载。

## 测试

- 对齐单元测试覆盖同音字、前后鼻音、平翘舌、韵母差异、漏字、增字、短噪声和重复句。
- 测试宽松匹配不会因为单个相似字跳过段落，也不会破坏相同句子的顺序推进。
- 模型列表测试覆盖旗舰模型元数据、排序、默认推荐和旧模型兼容。
- 模型加载配置测试覆盖标准精度模型、INT8 模型、Transducer 文件识别和失败回退。
- 运行完整 Flutter 测试、`dart analyze` 和 Android ARM64 Release 构建。
- 发布前核对 APK 包名、版本号、签名连续性、文件大小和 SHA-256，并上传完整 Release 资产。

## 风险和处理

- 发音等价过宽可能导致误跳。通过连续匹配长度、匹配比例、前进窗口和最终结果门槛限制影响，并保留原有精确匹配优先级。
- 大模型可能带来更高延迟和耗电。提供 480ms 模式和 INT8 包，默认档位可在实机测试后调整。
- 官方模型文件结构发生变化时可能无法加载。模型元数据保存模型类型，加载器在缺少必要文件时明确报错并保留当前模型。
- Android 低内存设备可能无法稳定加载标准精度模型。应用继续支持现有轻量模型，下载选择由用户控制。
